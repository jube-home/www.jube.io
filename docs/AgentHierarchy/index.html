    • Agent Hierarchy

    Agent hierarchy over the Jube service layer

    Generated from the catalogue, not hand-listed: every agent below owns tools that exist in ServiceToolCatalogue, every change appears exactly once in the whole tree, and no agent holds more than fifteen. A read may appear more than once, because an agent that can change an object holds the reads of that object as well – the alternative was an author whose only way to look anything up was free-form SQL against a schema it had to guess.

    Every operation is also listed flat, one entry each, in tool-inventory.md. That inventory is the backstop for this tree: when routing by meaning fails, an exact operation name, a service name or a permission number resolves there instead.

    Shape

       
    tools assigned 1046, over 718 distinct operations
    leaf agents 166
    supervisors 33
    leaves attached straight to a domain 10
    domains 9
    delegation hops root → domain → supervisor → leaf is three, exactly RunContext.MaxDepth; a collapsed slice is two
    widest fan-out 9, counting cross-domain reach; RunContext.MaxFanOut caps one spawn call at 8, not the roster
    largest toolbox 15
    shared reads 328 assignments, all idempotent and non-destructive; no change is shared

    Cross-domain reach

    A leaf owns an operation outright and cannot delegate, so an agent whose job needs an operation filed in another slice has no route to it unless one is named. Where that happened the failure was never a refusal: the agent routed correctly, worked out exactly what it needed, found it was not holding it, and answered from whatever it could reach instead – a rule author quoting a documentation example as if it were the caller’s own schema, a datasource author hanging its work on ExampleVisualisation because it could not create the registry it meant.

    Reach into another slice is widened by an edge, never by giving a second agent the same tool, because every change is owned by exactly one leaf and that is what makes the inventory below an address book. Sharing is confined to reads of an agent’s own slice, which is not reach at all: it is the author of an object being able to see the object it is about to change. The edges are declared in one table in AgentDefinitions.cs (CrossDomainReach), each carrying the sentence the agent is told, and they are marked Cross-Domain Reach on each agent below. Four kinds recur:

    • the completions leaf, which is the only authority on which payload fields a model actually carries and on which operators the rule builder offers – reached by every domain that authors something written against a field name;
    • the invocation context leaf, which builds the rule-evaluation context that every test bench’s Execute operation takes and none of them can build;
    • the synchronisation schedule leaf, which is the closing step of all nine rule taxonomy graphs and where every rule fragment is compiled, filed under platform reliability rather than beside the rules;
    • sibling slices of one artefact, where a datasource needs the registry it hangs off and the parameters it binds to.

    Domains follow the application’s own navigation menu in _Layout.cshtml, because that is hand-authored information architecture with the permission gate already attached to each entry. A slice is split three ways into Inspector, Test Bench and Author only where it exceeds seven tools; smaller slices stay whole, and small related slices are packed together up to the same budget. The split is by what an agent may change, not by what it may see: the Author of a slice holds that slice’s whole read surface too, including its validation, and the Inspector remains the safe default because it holds no change at all.

    Root

    Jooby

    • Hierarchy Placement: Level 1, root
    • Semantic Persona: The entry point for every request. It owns no tools of its own and exists to route a question to the one domain that owns the data behind it.
    • Semantic Routing Keywords: (routes everything)
    • Toolbox (Max 15): none — routing only
    • Downstream Dependencies: access-admin, assistant-admin, case-analyst, case-workflow-admin, data-analyst, model-admin, model-risk, model-support, platform-ops

    Access Control and Tenancy (access-admin)

    Access Control and Tenancy

    • Hierarchy Placement: Level 2, child of Jooby
    • Semantic Persona: Owns identity, roles, permissions, API keys and tenancy. Deliberately separated from every functional domain so that the agent which grants access is never the agent that uses it.
    • Semantic Routing Keywords: user, role, permission, tenant, API key, login, logout, entitlement, segregation of duties, access
    • Toolbox (Max 15): none — routes to 3 supervisors covering 45 tools
    • Downstream Dependencies: access-admin.entitlement, access-admin.identity, access-admin.tenancy

    Entitlement Supervisor

    • Hierarchy Placement: Level 3, child of Access Control and Tenancy
    • Semantic Persona: Routes within the entitlement slice of access control and tenancy. Holds no tools; it exists so the domain above it chooses between a handful of coherent specialists rather than dozens of leaves.
    • Semantic Routing Keywords: entitlement, role, registry, permission, specification
    • Toolbox (Max 15): none — routes to 7 leaf agents covering 19 tools
    • Downstream Dependencies: role-registry-inspector, role-registry-test-bench, role-registry-author, role-registry-permission-inspector, role-registry-permission-test-bench, role-registry-permission-author, permission-specification

    Fitting this to the runtime

    The tree above is a design, not a wiring. Four things in Jube.AskJooby decide whether it can execute as drawn:

    • RunContext.MaxDepth defaults to 3 and AgentFactory only offers a delegation tool while depth < context.MaxDepth, so root to domain to supervisor to leaf is exactly the budget and there is no room for a fifth tier; the nine slices that reduced to a single leaf are attached straight to their domain rather than kept behind a supervisor that would route to one child, which also buys back a hop for them.
    • RunContext.MaxFanOut defaults to 8 and SpawnAgentTool rejects a single spawn call that exceeds it, which is a cap on how many specialists are asked at once and not on how many an agent may choose between; no roster here exceeds nine, counting cross-domain reach, and model-admin and model-support are separate domains specifically so that the slice rosters stay within eight before any cross-domain edge is added.
    • AgentToolDefinition.RequiresSnapshot is already derived from the owning operation being Write or Delete, and SnapshotOnWriteAiFunction wraps those tools; the 174 tools flagged above are that same set, so the flag is a restatement of what the runtime already computes and must not be reintroduced as a second, hand-maintained source of truth.
    • AgentDefinitions.IsPermitted checks RequiresLandlord before it considers RequiredPermissions, because 49 services are landlord-only with an empty permission list; every permission shown above is read from the owning service’s own RequiredPermissions and is never retyped here, so a service that changes its guard changes this tree with it.

    Each agent’s toolbox is the authority for what it can call. Nothing above grants a tool that the catalogue does not already carry, and the eighteen operations the catalogue withholds on purpose stay withheld: they are absent from this tree by the same decision.
