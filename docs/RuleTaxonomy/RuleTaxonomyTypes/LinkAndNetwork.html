    • Link and Network

    Link and Network

    Definition: the same cardinality question as Cardinality, but relational: multiple entities converging on one shared attribute. The risk is about the connection, not about one entity’s own behaviour.

    Construction: an Abstraction Rule with a configuration identical to Cardinality, with the Search Key inverted to the shared trait (a device, an address, a beneficiary account) instead of the primary entity, and the Function Key set to the primary entity. See the Rule Taxonomy for how this type differs from its neighbours.

    Question an analyst asks Rule Taxonomy type that answers it
    How many different customers have used this device? Link and Network: Distinct Count of CustomerId, Search Key the device
    How many different accounts pay this beneficiary? Link and Network: Distinct Count of AccountId, Search Key the beneficiary
    How many different devices has this customer used? Not this type: Cardinality, the Search Key is the customer
    Is this device on a blacklist? Not this type: Static and Match Screening

    Link and Network: Inverting the Search Key

    Cardinality asks “how many distinct values of X has this entity produced”. Link and Network asks “how many distinct entities have produced this value”. The mechanism is the same Distinct Count, and only the two roles are swapped.

    Abstraction Rule field Cardinality Link and Network
    Search Key The entity (CustomerId) The shared trait (DeviceId)
    Function Key The attribute (DeviceId) The entity (CustomerId)
    Function Type Distinct Count, or Same Count Distinct Count, or Same Count
    Signal One entity showing many values Many entities converging on one value

    Because the recall is keyed on the shared trait, it returns the history of every entity that has presented that trait, including entities unrelated to the customer being processed. That is the point, and it is also why the trait must be a Search Key and the fetch limit in the model definition matters: a popular shared trait, such as a public Wi-Fi address, returns a great many records.

    Link and Network: Construction Steps

    Step 1: Make the Shared Trait a Search Key

    In Request XPath (Models » References » Request XPath), make the shared attribute a Search Key. The same field may also be a Search Key for a Cardinality rule where it is the entity, as the two are simply different rules on different keys. Each Search Key is one cache query per invocation.

    Step 2: Define the Abstraction Rule

    Set Search on, the Search Key to the shared trait, the Search Interval to the window in which convergence is meaningful (for example 30 Days), the Function Type to Distinct Count, and the Function Key to the entity. Use the rule fragment to restrict which events are eligible, for example Matched = Payload.TxnType.MatchEqual("Login"), or Matched = True for all. See Abstraction Rules.

    Step 3: Threshold in an Activation Rule

    A device shared by several customers, read as Abstraction.<Name>:

    Matched = Abstraction.DistinctCustomersPerDevice30d.MatchGreater(3)

    Combined with a payload condition, to raise the signal only when value is moving, using Require and Against per the Rule Authoring Methodology:

    Matched = Abstraction.DistinctAccountsPerBeneficiary7d.RequireGreater(5).Against(Payload.CurrencyAmount).MatchGreater(500)

    Exempting known good shared traits, such as an office network, using a List, per Reference Data:

    Matched = Abstraction.DistinctCustomersPerDevice30d.RequireGreater(3).Against(Payload.DeviceId).MatchNotInList(List.KnownSharedDevices)

    Where the shared trait is known bad in advance, this is not a network signal but a membership check, per Static and Match Screening.

    Step 4: Test Link and Network with Several Entities

    Post events from several different entities that present one shared value, and assert the response on the event that crosses the threshold. Then post events for one entity across several values, to prove the rule counts entities and not values. Whether the current event is included in the aggregation should be confirmed on the target instance, per Cardinality.

    Link and Network: Limits of the Type

    This type detects one hop: entities that share a single trait directly. It does not traverse a graph, so it cannot answer “customers linked to a customer who is linked to fraud”. Chains of two or more traits are built by stacking rules, one per trait, and combining them in an Activation Rule with And or Or. Anything beyond that is a departure from the documented taxonomy, and is unsupported.

    Link and Network: Common Faults

    Symptoms of a misbuilt Link and Network rule, with the likely cause.

    Symptom in a Link and Network rule Likely cause
    The Abstraction value is always 0 or 1 The Search Key is the entity, not the shared trait. The Search Key and Function Key are the wrong way round.
    Counts are far too high for a common trait The shared trait is not distinctive (a shared gateway, or a default value). Exempt it with a List.
    The count is lower than expected The fetch limit in the model definition truncates the records returned for a popular trait.
    Slow invocations Too many Search Keys, or a popular trait returning very large recalls. Narrow the window.

    Examples by Sub-Class

    Validated. Every fragment in this section is compiled individually through the Jube Parser, with its payload fields and its TTL Counter, Abstraction, Calculation, List and Sanction tokens declared, so each extension method and argument type is checked against the engine. Compilation does not validate a rule’s logic or its thresholds, which are illustrative placeholders to be tuned on data.

    3.1 Shared device and technical identifiers

    # Example Description Jube construction Fragment Notes
    3.1-01 Many customers on one device Several unrelated customers transact from the same device (mule farm, synthetic identity ring). Abstraction Rule DistinctCustomersPerDevice30d: Search Key DeviceId (Request XPath), Search Interval 30 Days, Function Type Distinct Count over CustomerId (placeholder field). The threshold is the bullet’s own value of 3. Matched = Abstraction.DistinctCustomersPerDevice30d.MatchGreaterOrEqual(3) Tag: Link · Fraud · Device→Customer · 30d, distinct customers ≥ 3
    3.1-02 Many accounts on one device One device enrolled to many accounts. Abstraction Rule DistinctAccountsPerDevice30d: Search Key DeviceId, Search Interval 30 Days, Distinct Count over AccountId. The threshold is illustrative and is set at build time. Matched = Abstraction.DistinctAccountsPerDevice30d.MatchGreaterOrEqual(3) Tag: Link · Fraud · Device→Account · 30d
    3.1-03 Many new accounts opened from one device Application farming. Abstraction Rule DistinctApplicationsPerDevice7d: Search Key DeviceId, Search Interval 7 Days, Distinct Count over ApplicationId (placeholder field), with the filter Matched = Payload.TxnType.MatchEqual("Application") (placeholder value) so only application events are counted. Matched = Abstraction.DistinctApplicationsPerDevice7d.MatchGreaterOrEqual(3) Tag: Link · Fraud · Device→Application · 7d
    3.1-04 Many customers on one IP address Residential IP shared by unrelated customers beyond household norm. Abstraction Rule DistinctCustomersPerIp7d: Search Key IP holding the value normalised upstream by NormaliseIpAddress, Search Interval 7 Days, Distinct Count over CustomerId. The household-norm threshold is set from data, not from this fragment. Matched = Abstraction.DistinctCustomersPerIp7d.MatchGreaterOrEqual(3) Tag: Link · Fraud · IP→Customer · 7d
    3.1-05 Many customers on one browser fingerprint Canvas/WebGL/audio fingerprint shared across identities. Abstraction Rule DistinctCustomersPerFingerprint30d: Search Key FingerprintHash (placeholder field, a hash supplied by the device SDK), Search Interval 30 Days, Distinct Count over CustomerId. Matched = Abstraction.DistinctCustomersPerFingerprint30d.MatchGreaterOrEqual(3) Tag: Link · Fraud · Fingerprint→Customer · 30d
    3.1-06 Many customers on one SIM/phone number Phone number shared across identities. Abstraction Rule DistinctCustomersPerPhone90d: Search Key PhoneDigits (placeholder field holding PhoneNumberDigits applied upstream), Search Interval 90 Days, Distinct Count over CustomerId. Its filter Matched = Payload.Phone.IsValidE164PhoneNumber() keeps invalid numbers out of the count. Matched = Abstraction.DistinctCustomersPerPhone90d.MatchGreaterOrEqual(3) Tag: Link · Fraud · Phone→Customer · 90d
    3.1-07 Many customers sharing one email domain pattern Disposable or sequentially generated emails across customers. Abstraction Rule DistinctCustomersPerEmailPattern30d: Search Key EmailPattern (placeholder field, the local part with RegexReplace of trailing digits applied upstream), Search Interval 30 Days, Distinct Count over CustomerId. Its filter Matched = Payload.Email.EmailDomain().MatchInList(List.DisposableDomains) restricts the count to disposable domains, and the list is vendor or internal reference data. Matched = Abstraction.DistinctCustomersPerEmailPattern30d.MatchGreaterOrEqual(3) Tag: Link · Fraud · Email pattern→Customer · 30d
    3.1-08 Many customers sharing a device-id after factory reset Emulator/reset device farms. Abstraction Rule DistinctCustomersPerHardware7d: Search Key DeviceHardwareHash (placeholder field, a hardware-derived hash supplied upstream), Search Interval 7 Days, Distinct Count over CustomerId. The rule detects shared hardware; a factory reset is not observed. Matched = Abstraction.DistinctCustomersPerHardware7d.MatchGreaterOrEqual(3) Tag: Link · Fraud · Device model/hardware→Customer · 7d
    3.1-09 Many customers on one emulator signature Emulator/rooted environment across customers. Abstraction Rule DistinctCustomersPerEmulator7d: Search Key EmulatorSignature (placeholder field, supplied by the device-intelligence vendor), Search Interval 7 Days, Distinct Count over CustomerId. Matched = Abstraction.DistinctCustomersPerEmulator7d.MatchGreaterOrEqual(3) Tag: Link · Fraud · Emulator signature→Customer · 7d
    3.1-10 Device shared between a victim and a known fraudster Device linked to confirmed fraud account. List FraudLinkedDevices, fed from the case-management outcome, holds device ids linked to confirmed fraud accounts. Membership has no window; the Activation Rule tests DeviceId (placeholder field) against it. Matched = Payload.DeviceId.MatchInList(List.FraudLinkedDevices) Tag: Link · Fraud · Device→Account (flagged) · lifetime
    3.1-11 VPN/proxy exit node shared across customers Many accounts via one anonymising exit. List AnonymiserExitIps holds vendor exit-node addresses, and Abstraction Rule DistinctCustomersPerExitNode24h uses Search Key IP (normalised upstream), Search Interval 24 Hours and Distinct Count over CustomerId. The Activation Rule requires both list membership and the count; the vendor, not Jube, classifies a VPN or proxy, and IsInAnyCidr can test published ranges instead of a list. Matched = Payload.IP.MatchInList(List.AnonymiserExitIps) And Abstraction.DistinctCustomersPerExitNode24h.MatchGreaterOrEqual(3) Tag: Link · Fraud · IP→Customer · 24h
    3.1-12 Many customers on one MAC/hardware attribute Hardware attribute reuse. Abstraction Rule DistinctCustomersPerMacHash30d: Search Key MacHash (placeholder field, Sha256Hex of the MAC address applied upstream), Search Interval 30 Days, Distinct Count over CustomerId.
