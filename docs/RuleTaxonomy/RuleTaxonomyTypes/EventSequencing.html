    • Event Sequencing

    Event Sequencing

    Definition: a chain of states or events that matters only together, not individually, within one model or across linked models. It enforces a one after another approach.

    Construction: within a model, a Dictionary (KVP) holds the last state and is compared to the current Payload. Across models, a TTL Counter is incremented in one model and read in a linked model through a common key, which is possible because a TTL Counter can be incremented across models. Lifecycle chains, channel hopping and takeover chains are domain dressing on this one mechanism, and are not separate classes. See the Rule Taxonomy.

    Event Sequencing: Priority Enforces One After Another

    Event Sequencing reuses the TTL Counter mechanism of Velocity and Volume, and priority is decisive. Counters are updated inside the invocation as each incrementing Activation Rule matches, and Activation Rules are evaluated in ascending Priority order (a lower number is evaluated first). For a genuine one-after sequence the rule that tests the chain must be evaluated before the rule that increments the step counter for the current event, so it has a high order (evaluated early) Priority. Otherwise the current event counts as its own predecessor and the sequence is satisfied by a single event.

    Event Sequencing: Cross-Model Example

    Alert when a customer has more than three failed logins, then adds a new beneficiary, then makes a financial transaction over a certain amount. Each step is a different model, joined by a common key such as CustomerId, and each step is armed only when the step before it has happened.

    Step Model Rule that increments the counter Counter incremented (defined in the model that reads it)
    1 Login model Failed login: Matched = Payload.LoginResult.MatchEqual("Failed") FailedLogins in the beneficiary model
    2 Beneficiary model New beneficiary, gated on step 1: Matched = TTLCounter.FailedLogins.RequireGreater(3).Against(Payload.IsNewBeneficiary).MatchIsTrue() BeneficiaryAfterFailedLogins in the transaction model
    3 Transaction model Alert, gated on step 2: Matched = TTLCounter.BeneficiaryAfterFailedLogins.RequireGreater(0).Against(Payload.CurrencyAmount).MatchGreater(5000) None. This is the alerting Activation Rule.

    The gate in each step is what makes it a sequence rather than three independent counts: the step 2 counter cannot increment unless the step 1 counter had already crossed its threshold, and the step 3 alert cannot fire unless step 2 had incremented. The TTL Counter interval on each counter bounds how long the chain may take, for example Hours / 24.

    Event Sequencing: Construction Steps

    Define a TTL Counter per link in the chain, in the model that will read it, keyed on the common entity. Increment each counter from an Activation Rule in the model where that event occurs, choosing the target model in the Increment TTL Counter options (see TTL Counter Activation Rule Incrementation). Gate each incrementing rule on the previous link’s counter. Set Priority so that gates are evaluated before their own increment. Threshold the last counter in the alerting rule. The common key must be present in the payload of every model in the chain, otherwise the increment is skipped for that event.

    Event Sequencing: Within-Model Example

    Within one model, a Dictionary KVP holding the last state for the entity is compared with the current payload, for example alerting when a status moves from Dormant directly to a high value withdrawal:

    Matched = Dictionary.LastAccountStatus.RequireIsZero().Against(Payload.CurrencyAmount).MatchGreater(5000)

    A Dictionary is populated during model synchronisation from the user interface, a CSV upload, the database or the API. It is not written by the invocation itself, so it holds state that something external maintains. Where the events themselves must maintain the state, use the cross-model TTL Counter mechanism above. The value of a Dictionary lookup is a number, and is zero when the key is absent from the payload or the Dictionary, so choose encodings where zero is the safe default. See Dictionary.

    Event Sequencing: Common Faults

    Symptoms of a misbuilt Event Sequencing rule, with the likely cause.

    Symptom in an Event Sequencing rule Likely cause
    The alert fires on a single event The gate is evaluated after its own increment, so the event satisfies its own predecessor. Lower the gate’s Priority number.
    The alert never fires The common key is missing from a model’s payload, so the increment is skipped; or the window is shorter than the chain.
    Steps fire in the wrong order The increment for a later step is not gated on the earlier step’s counter.
    Chain fires for unrelated customers The TTL Counter Data Name is not the shared entity key.

    Examples by Sub-Class

    Validated. Every fragment in this section is compiled individually through the Jube Parser, with its payload fields and its TTL Counter, Abstraction, Calculation, List and Sanction tokens declared, so each extension method and argument type is checked against the engine. Compilation does not validate a rule’s logic or its thresholds, which are illustrative placeholders to be tuned on data.

    5.1 Account takeover chains

    # Example Description Jube construction Fragment Notes
    5.1-01 Password reset followed by payment Credential reset then payment within a short window. TTL Counter PasswordResetLastHour (Data Name AccountId, Interval Hours / 1, Sum off) is incremented by the activation rule that matches the password-reset event, and the payment rule reads it. Reset events must reach the model that defines the counter, because the engine increments only on payloads that carry the key. Payload.EventType is a placeholder field name. Matched = TTLCounter.PasswordResetLastHour.RequireGreater(0).Against(Payload.EventType).MatchEqual("Payment") Tag: Sequence · Fraud · Account · 1h
    5.1-02 Credential change followed by new payee and payment Change, add beneficiary, pay. TTL Counters CredentialChangeLast24Hours and PayeeAddedLast24Hours (Data Name AccountId, Interval Hours / 24, Sum off) are incremented by the credential-change and payee-add rules. The payment rule reads both. Order between the two prior steps is not enforced, only co-occurrence in the window. Matched = TTLCounter.CredentialChangeLast24Hours.RequireGreater(0).Against(TTLCounter.PayeeAddedLast24Hours).RequireGreater(0).Against(Payload.EventType).MatchEqual("Payment") Tag: Sequence · Fraud · Account · 24h
    5.1-03 Phone number change followed by OTP request and payment Contact change then authentication then outflow. TTL Counters PhoneChangeLast24Hours and OtpRequestLast24Hours (Data Name AccountId, Interval Hours / 24, Sum off) are incremented by the phone-change and OTP-request rules, and the payment rule reads both. The OTP request must be an event the bank feeds to Jube, and the order between the two prior steps is co-occurrence only. Matched = TTLCounter.PhoneChangeLast24Hours.RequireGreater(0).Against(TTLCounter.OtpRequestLast24Hours).RequireGreater(0).Against(Payload.EventType).MatchEqual("Payment") Tag: Sequence · Fraud · Account · 24h
    5.1-04 Email change followed by password reset Email replaced and then recovery initiated. TTL Counter EmailChangeLastHour (Data Name AccountId, Interval Hours / 1, Sum off) is incremented by the email-change rule. The password-reset-request rule reads it, so the prior email change is checked in order because the recovery request is the current event. Matched = TTLCounter.EmailChangeLastHour.RequireGreater(0).Against(Payload.EventType).MatchEqual("PasswordResetRequest") Tag: Sequence · Fraud · Account · 1h
    5.1-06 New device enrolment followed by payment First-seen device registers then pays. TTL Counter DeviceEnrolledLast24Hours (Data Name AccountId, Interval Hours / 24, Sum off) is incremented by the device-enrolment rule, and the payment rule reads it. First-seen device is approximated by the enrolment event inside the window, so there is no device history beyond 24 hours. Matched = TTLCounter.DeviceEnrolledLast24Hours.RequireGreater(0).Against(Payload.EventType).MatchEqual("Payment") Tag: Sequence · Fraud · Account · 24h
    5.1-07 New device enrolment followed by limit increase Device added then limits raised. The same TTL Counter DeviceEnrolledLast24Hours as 5.1-06 (Data Name AccountId, Interval Hours / 24) is read by the limit-increase rule. The limit increase is the current event and the enrolment is the prior counted event. Matched = TTLCounter.DeviceEnrolledLast24Hours.RequireGreater(0).Against(Payload.EventType).MatchEqual("LimitIncrease") Tag: Sequence · Fraud · Account · 24h
    5.1-08 Failed logins followed by successful login and payment Brute-force success chain. TTL Counters FailedLoginLastHour and LoginSuccessLastHour (Data Name AccountId, Interval Hours / 1, Sum off) are incremented by the failed-login and successful-login rules, and the payment rule reads both. The threshold of 5 is a placeholder for the policy value N, and the failure-then-success order is only co-occurrence within the hour. Matched = TTLCounter.FailedLoginLastHour.RequireGreaterOrEqual(5).Against(TTLCounter.LoginSuccessLastHour).RequireGreater(0).Against(Payload.EventType).MatchEqual("Payment") Tag: Sequence · Fraud · Account · 1h
    5.1-09 Login from new country followed by payee addition Foreign login then payee added. TTL Counter ForeignLoginLastHour (Data Name AccountId, Interval Hours / 1, Sum off) is incremented by a login rule whose own condition is that the login country differs from the KYC residence country, so only foreign logins count. The payee-addition rule reads it. The approximation of new country by residence mismatch needs that increment condition to be checked before reliance. Matched = TTLCounter.ForeignLoginLastHour.RequireGreater(0).Against(Payload.EventType).MatchEqual("PayeeAdd") Tag: Sequence · Fraud · Account · 1h
    5.1-10 Dormant account login followed by contact change and transfer Wake-up takeover pattern. TTL Counter Activity12Months (Data Name AccountId, Interval Months / 12, code m, Sum off) is incremented by every account event. The login rule reads it with MatchIsZero() and must have the lower Priority number so the read happens before its own increment. A TTL Counter DormantLoginLast7Days (Data Name AccountId, Interval Days / 7) is incremented on that dormant login, and the transfer rule reads it together with ContactChangeLast7Days. Matched = TTLCounter.DormantLoginLast7Days.RequireGreater(0).Against(TTLCounter.ContactChangeLast7Days).RequireGreater(0).Against(Payload.EventType).MatchEqual("Transfer") Check: 12-month dormancy is a policy choice; statutory dormancy rules for unclaimed funds differ by jurisdiction. Tag: Sequence · Fraud · Account · 7d
    5.1-11 Security question change followed by payment Authentication details changed then pay. TTL Counter AuthDetailChangeLast24Hours (Data Name AccountId, Interval Hours / 24, Sum off) is incremented by the security-question change rule, and the payment rule reads it. The change is a feed event, so no comparison is needed. Matched = TTLCounter.AuthDetailChangeLast24Hours.RequireGreater(0).Against(Payload.EventType).MatchEqual("Payment") Tag: Sequence · Fraud · Account · 24h
    5.1-12 MFA disabled followed by payment Protection removed then outflow.
