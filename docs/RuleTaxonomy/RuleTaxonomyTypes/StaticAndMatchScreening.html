    • Static and Match Screening

    Static and Match Screening

    Definition: a deterministic or fuzzy match against a known reference set.

    Construction: a List for internal reference data, and a Sanction for regulatory lists. A Sanction returns a value, retrieved by GetValueOrThrow, which is compared, and is not a Boolean. Device blacklists are covered here, and need no separate class. See the Rule Taxonomy.

    Question an analyst asks Rule Taxonomy type that answers it
    Is this account on our internal deny list? Static Screening: a List
    Is this device on the blacklist? Static Screening: a List of device identifiers
    Is this name close to a sanctioned party? Match Screening: a Sanction
    Is this name close to a name on our internal watch list? Match Screening: SomehowInList against a List
    Does the narrative mention a risky term? Not this type: Unstructured Text Screening

    Static Screening: Lists

    A List is maintained in the Lists page (or by CSV upload, database or API), and referenced from rules by name, without embedding the values in the rule. Lists are synchronised by the engine in the background continuously and do not need a model synchronisation, so a new value applies almost immediately. A List Value can be given a Delete Expiry Date, after which it lapses, which suits temporary blocks. See Lists.

    A rule reads a List as List.<Name>, which is a collection of strings, and tests membership with the InList steps of a pipeline (see the Rule Pipeline Reference). InList is case sensitive, and InListIgnoreCase is not. Both are null safe, so a missing value fails the test and does not fault the rule:

    Matched = Payload.AccountId.MatchInList(List.BadCustomers)

    Combined with a threshold, using Against to switch to the amount, keeping the state:

    Matched = Payload.AccountId.RequireInList(List.BadCustomers).Against(Payload.CurrencyAmount).MatchGreater(100)

    An Accept list exemption, rejecting an event whose device is on a trusted List before any other step runs:

    Matched = Payload.DeviceId.RejectInList(List.TrustedDevices).Against(Payload.CurrencyAmount).MatchGreater(1000)

    List matching is a whole value match, not a substring or fuzzy match. A Gateway Rule using a List is the cheapest place to stop or route an event, which is also where Accept lists (allow lists) belong, so that trusted parties skip later processing. See Gateway Rules.

    Static Screening: Dictionary Lookups

    Where the reference data has a numeric value per key, such as a country risk score, use a Dictionary in place of a List. A Dictionary pairs a key from the payload with a value, and returns zero if the key is absent, so encode risk so that zero is the safe default. See Dictionary.

    Matched = Dictionary.CountryRisk.MatchGreaterOrEqual(4)

    Match Screening: Sanctions

    A Sanction definition names a payload field holding a multipart string (a name of space separated tokens, order insensitive), a maximum Levenshtein Distance, and Max Distance Ratio and Max Coverage Ratio controls. The engine performs the fuzzy match against the loaded regulatory lists during the invocation, before rules run, and makes the aggregated distance available as Sanction.<Name>. See Sanctions and Sanction Searching.

    The value is a distance, so smaller is closer, and zero is an exact match. Compare it, and do not treat it as a Boolean:

    Matched = Sanction.PartyName.MatchLessOrEqual(1)

    A tiered response is two Activation Rules on the same value, each with its own response elevation. An exact match:

    Matched = Sanction.PartyName.MatchIsZero()

    A near match, using the inclusive InRange test:

    Matched = Sanction.PartyName.MatchInRange(1, 2)

    When there is no match, or the multipart field is absent from the payload, no value is added for the definition, and reading Sanction.<Name> throws. A faulting fragment is logged and does not match, per the methodology, so a rule of this shape is safe, but it logs an exception for every event with no match. That guarding lives in the Sanctions stage of the invocation pipeline, not in an extension method, and is covered there. The aggregation over multiple matches is set on the Sanction definition (Sum, Average, Count, Max, Min, First or Last). See the Rule Pipeline Reference and Jube.Engine/EntityAnalysisModelInvoke/Context/Extensions/SanctionsExtensions.cs.

    Match Screening: Fuzzy Matching Against an Internal List

    Sanctions cover regulatory lists. For an internal reference set, such as a watch list of names, use the fuzzy List steps, which compare the payload value with every entry of a List and need no Sanction definition. The default profile folds case, accents and punctuation, then accepts a Jaro-Winkler or token sort similarity of at least 0.92:

    Matched = Payload.CustomerName.MatchSomehowInList(List.WatchList)

    A tuned profile is written as an options string, where each option is described in the Rule Pipeline Reference. This one tolerates a swapped pair of letters, drops titles, and skips very short names, where similarity is noisy:

    Matched = Payload.CustomerName.MatchSomehowInListWith(List.WatchList, "damerau=1,soundex,notitles,minlength=4")

    Single algorithm steps exist for the simple cases (LevenshteinInList, DamerauInList, SimilarInList, JaroWinklerInList, NormalisedInList). An invalid options string fails closed, so nothing matches. Every event is compared with every entry, so for a large List add firstletter or minlength, and put an exact MatchInList first.

    Static and Match Screening: Common Faults

    Symptoms of a misbuilt screening rule, with the likely cause.

    Symptom in a screening rule Likely cause
    A List never matches Case or whitespace differs. Use InListIgnoreCase, or normalise the value with Trim and Lower in the pipeline.
    The Sanction rule never matches The Distance is too tight; the multipart field is not in the payload; the sanctions lists have not been loaded.
    The Sanction rule matches too much Distance is too loose for short names. Tighten Max Distance Ratio.
    A List change is not applied Lists sync in the background, but a Dictionary needs a model synchronisation.

    Examples by Sub-Class

    Validated. Every fragment in this section is compiled individually through the Jube Parser, with its payload fields and its TTL Counter, Abstraction, Calculation, List and Sanction tokens declared, so each extension method and argument type is checked against the engine. Compilation does not validate a rule’s logic or its thresholds, which are illustrative placeholders to be tuned on data.

    # Example Description Jube construction Fragment Notes
    6.1-01 Customer name match to sanctions list Fuzzy match of customer name against OFAC SDN, UN, EU, UK OFSI and other consolidated lists. Sanction definition ConsolidatedSanctions over the consolidated regulatory lists, fuzzy on Payload.CustomerName. The sanction entity analysis model is engine-synced; the daily rescreen is the scheduled re-run of this same model, not a fragment. The Activation rule thresholds the match distance (1 is an illustrative placeholder). Matched = Sanction.ConsolidatedSanctions.MatchLessOrEqual(1) Check: Named regimes (OFAC SDN, UN, EU, UK OFSI) and the consolidation of their lists are regulatory facts: verify which sources are loaded and their update cadence Tag: Screening · AML · Customer · onboarding + daily rescreen
    6.1-02 Beneficiary name match to sanctions list Payee name screened pre-payment. Sanction definition BeneficiarySanctions over the same consolidated lists, fuzzy on Payload.BeneficiaryName. A definition names one payload field, so this is a separate definition from the customer one. The Activation rule thresholds the match distance (placeholder). Matched = Sanction.BeneficiarySanctions.MatchLessOrEqual(1) Tag: Screening · AML · Beneficiary · per transaction
    6.1-03 Originator name match to sanctions list Sender in an inbound payment screened. Sanction definition OriginatorSanctions over the same consolidated lists, fuzzy on Payload.OriginatorName, a separate definition from the customer and beneficiary ones. The Activation rule thresholds the match distance (placeholder). Matched = Sanction.OriginatorSanctions.MatchLessOrEqual(1) Tag: Screening · AML · Originator · per transaction
    6.1-04 Intermediary/correspondent bank match to sanctions list Banks in the payment chain screened. List SanctionedBics holds the sanctioned bank codes. The intermediaries are a JSON array in Payload.PaymentChainJson, and every element is tested against the list with MatchJsonTextArrayAnyInList, navigating to the array at the path $.intermediaryBics. A single intermediary BIC would be a plain institution-code list test; an any-element screen over a chain needs this step. Matched = Payload.PaymentChainJson.MatchJsonTextArrayAnyInList("$.intermediaryBics", List.SanctionedBics) Tag: Screening · AML · Bank · per transaction
    6.1-05 BIC/SWIFT code match to sanctioned bank Deterministic match on BIC. List SanctionedBicInstitutions holds the institution codes of sanctioned banks. The institution part of the BIC is compared, so branch codes cannot evade the list. IsValidBic can gate the format first. Matched = Payload.BeneficiaryBic.BicInstitutionCode().MatchInList(List.SanctionedBicInstitutions) Tag: Screening · AML · Bank · per transaction
    6.1-06 Vessel name/IMO match to sanctioned vessels Trade finance and shipping screening. Sanction definition VesselSanctions on Payload.VesselName fuzzy, in the first Activation rule. The IMO number is an exact List test, List.SanctionedImoNumbers on Payload.ImoNumber, in a second Activation rule with Matched = Payload.ImoNumber.MatchInList(List.SanctionedImoNumbers). They are kept apart because a Sanction read throws when there is no match, which would fault a combined fragment. IMO check-digit validation has no existing extension and is not needed for the match. Matched = Sanction.VesselSanctions.MatchLessOrEqual(1) Tag: Screening · AML · Vessel · per transaction
    6.1-07 Aircraft tail number match Aircraft identifiers against sanctioned lists. List SanctionedTailNumbers, a case-insensitive whole-value test on Payload.AircraftTailCode. Tail numbers have no validator in the library, so the match is exact against the list only. Matched = Payload.AircraftTailCode.MatchInListIgnoreCase(List.SanctionedTailNumbers) Tag: Screening · AML · Aircraft · per transaction
    6.1-08 Country or territory sanctioned region match (e.g. comprehensively sanctioned) Counterparty or payment routed to or from embargoed jurisdictions. The counterparty country is normalised to alpha-2 with CountryAlpha2, then tested against List EmbargoedJurisdictions, which holds the programme scope. Matched = Payload.CounterpartyCountry.CountryAlpha2().MatchInList(List.EmbargoedJurisdictions) Check: Comprehensive embargo scope changes with each programme: verify the current territories and whether sub-territories are included Tag: Screening · AML · Payment · per transaction
    6.1-09 Sectoral/regional sanctions address match Address within restricted region (e.g. specific regions subject to sanctions). List RestrictedRegions tested for containment, ignoring case, in Payload.Address. It misses regions written in other scripts or abbreviations unless the list carries those variants. Matched = Payload.Address.MatchContainsAnyInListIgnoreCase(List.RestrictedRegions) Check: Which regions are restricted, and under which programme, is a regulatory fact: verify against current OFAC, EU and UK programmes Tag: Screening · AML · Address · per transaction
