    • Geospatial and Context

    Geospatial and Context

    Definition: physical distance, travel, or boundary. Use it for anything location based.

    Construction: Double geospatial extensions directly on Payload coordinates for a single comparison, aggregated through an Abstraction Rule when comparing against a longer term pattern. See the Rule Taxonomy.

    Question an analyst asks Rule Taxonomy type that answers it
    Is this payment within 5 km of the customer’s home? Geospatial: IsWithinRadiusKm
    Could the customer physically have travelled between the two events? Geospatial: ImpliedTravelSpeedKmh
    How many different countries in 24 hours? Not this type: Cardinality
    Is the transaction at an unusual time of day? Context (below): DateTime extensions

    Geospatial: Single Comparison Between Two Points

    Coordinates are Double payload values, so the geospatial steps are available on them directly. The value the pipeline starts on is the first latitude, and the arguments are the first longitude, the second latitude, the second longitude, then the limit, in that order. See the Rule Pipeline Reference. Further than 500 km from a fixed point, such as a branch:

    Matched = Payload.Latitude.MatchDistanceKmAbove(Payload.Longitude, 51.5074, -0.1278, 500)

    A boundary test against a radius, using OutsideRadiusKm(longitude1, latitude2, longitude2, radiusKm):

    Matched = Payload.Latitude.MatchOutsideRadiusKm(Payload.Longitude, Payload.HomeLatitude, Payload.HomeLongitude, 50)

    WithinRadiusKm and DistanceKmBelow are the inverses. Each step has a miles form (WithinRadiusMiles, OutsideRadiusMiles, DistanceMilesAbove, DistanceMilesBelow) taking the same arguments. The distance is great circle, and is not a road distance.

    Geospatial: Impossible Travel

    Travel between two events needs the earlier event’s coordinates and the elapsed time. ImpliedSpeedAbove(longitude1, latitude2, longitude2, hoursElapsed, kilometersPerHour) tests whether the implied speed exceeds a plausible ceiling:

    Matched = Payload.Latitude.MatchImpliedSpeedAbove(Payload.Longitude, Payload.PreviousLatitude, Payload.PreviousLongitude, Payload.ElapsedHours, 900)

    The previous coordinates and elapsed time must be in the payload, either supplied by the sender, produced by an Inline Function, or retrieved from history by an Abstraction Rule using the Actual Value Function Type with an Offset of Last. The Abstraction route is the aggregated form described above: it compares the current event with a longer term pattern held in the cache, at the cost of a cache retrieval per Search Key. See Abstraction Rules. Zero elapsed hours is treated as infinite speed, so two events at different places at the same instant match. ImpliedSpeedBelow is the inverse.

    Context: Time and Calendar

    Context rules use DateTime steps on payload dates, for example whether an event is at a weekend, outside business hours, the end of a month, or older than a number of days. These are cheap, need no cache, and are best consumed as an input to another type, for example a large transfer combined with an out of hours event:

    Matched = Payload.TransactionDate.RequireIsWeekendInZone(Payload.CustomerZoneId).Against(Payload.CurrencyAmount).MatchGreater(10000)

    The steps are IsWeekday, IsWeekend, IsMorning, IsAfternoon, WithinBusinessHours(startHour, endHour), OutsideBusinessHours, IsToday, IsPast, IsFuture, OlderThanDays, YoungerThanDays, WithinDaysOf, DayOfWeekIn, IsStartOfMonth and IsEndOfMonth, with HourOfDay() and AgeInDays() as transformers. The plain extension methods have different names (for example IsWeekendDay).

    A customer in another timezone experiences a different hour, so a business hours or weekend test should be made in the customer’s timezone. The InZone forms read the value as UTC, convert it to the named time zone (an IANA or Windows identifier such as America/New_York), and then test, and an unknown zone fails the test:

    Matched = Payload.TransactionDate.MatchOutsideWeekdayBusinessHoursInZone(Payload.CustomerZoneId, 8, 18)

    The InZone steps are WithinBusinessHoursInZone, OutsideBusinessHoursInZone, WithinWeekdayBusinessHoursInZone, OutsideWeekdayBusinessHoursInZone, IsWeekdayInZone and IsWeekendInZone, and the Weekday forms without a zone use the value’s own clock, so a weekend counts as outside hours. ToZone(zoneId) converts the value and continues the pipeline, so that any other DateTime test can be made in local time:

    Matched = Payload.TransactionDate.ToZone(Payload.CustomerZoneId).MatchIsMorning()

    The value is read as UTC, so the payload date must be UTC. Without an InZone form or ToZone, the test reasons in the clock of the value as supplied. Age and tenure derived this way are the cross cutting Identity and Demographic variables described in the Rule Taxonomy.

    Geospatial and Context: Common Faults

    Symptoms of a misbuilt Geospatial or Context rule, with the likely cause.

    Symptom in a Geospatial or Context rule Likely cause
    Distances are wildly wrong Latitude and longitude arguments are swapped, or the coordinates are in a projection other than decimal degrees.
    The impossible travel rule fires constantly Elapsed time is in the wrong unit (hours are required), or the previous location is stale.
    The business hours rule is wrong for customers The test is not an InZone form or ToZone, so it reasons in the supplied clock; or the payload date is not UTC; or the zone identifier is unknown, which fails the test.
    The rule does not match on missing coordinates A null or NaN coordinate fails the test, so the rule does not match. Decide whether that is the outcome wanted.

    Examples by Sub-Class

    Validated. Every fragment in this section is compiled individually through the Jube Parser, with its payload fields and its TTL Counter, Abstraction, Calculation, List and Sanction tokens declared, so each extension method and argument type is checked against the engine. Compilation does not validate a rule’s logic or its thresholds, which are illustrative placeholders to be tuned on data.

    8.1 Impossible travel and distance

    # Example Description Jube construction Fragment Notes
    8.1-01 Impossible travel between consecutive transactions Distance divided by elapsed time exceeds plausible speed. Two Abstraction Rules keyed on Card, with Function Type Actual Value and Offset Type Last, return the previous latitude and longitude, and an Activation Rule holds the pipeline. HoursSincePrev is an Abstraction Rule with Function Type Since in Hours over the same Card key, giving the elapsed hours back to the prior event, and a minimum-gap Require step should be added so that same-instant pairs do not match. Matched = Payload.Latitude.MatchImpliedSpeedAbove(Payload.Longitude, Abstraction.PrevLatitude, Abstraction.PrevLongitude, Abstraction.HoursSincePrev, 900) Check: 900 km/h is an analyst plausibility threshold, not a regulatory figure; calibrate against airline speeds and the false-positive rate. Tag: Geo · Fraud · Card/Account · consecutive events, speed ≥ 900 km/h
    8.1-02 Impossible travel between consecutive logins Same for login geolocations. The same construction as 8.1-01, keyed on Account over login events, with Abstraction Rules returning the previous login coordinates. LoginLatitude and LoginLongitude are placeholder fields for the login payload, and HoursSincePrevLogin is an Abstraction Rule with Function Type Since in Hours keyed on Account. Matched = Payload.LoginLatitude.MatchImpliedSpeedAbove(Payload.LoginLongitude, Abstraction.PrevLoginLatitude, Abstraction.PrevLoginLongitude, Abstraction.HoursSincePrevLogin, 900) Check: 900 km/h as 8.1-01. Tag: Geo · Fraud · Account · consecutive logins
    8.1-03 Card-present transactions in two countries within hours Physical presence conflict. One Abstraction Rule with Search Key Card, Search Interval of 6 Hours and Function Type Distinct Count over CountryAlpha2 (a placeholder field), limited by its own match condition to card-present events, and an Activation Rule reads the count with the greater-than step. The threshold of 1 is an illustrative placeholder. Matched = Abstraction.CpCountries6h.MatchGreater(1) Tag: Geo · Fraud · Card · 6h
    8.1-04 Card-present and CNP in distant locations simultaneously CP in one place; CNP from another. Two Abstraction Rules keyed on Card with a 1 Hour Search Interval, Offset Type Last and Function Type Actual Value, limited to card-present events, return the last card-present coordinates. A Require step makes the card-not-present test a gate, and the 50 km distance is an illustrative placeholder; CNP events often carry no coordinates, so the rule is silent without them. Matched = Payload.IsCardPresent.RequireIsFalse().Against(Payload.Latitude).MatchDistanceKmAbove(Payload.Longitude, Abstraction.LastCpLatitude, Abstraction.LastCpLongitude, 50) Check: None; window and distance are analyst choices. Tag: Geo · Fraud · Card · 1h
    8.1-05 ATM withdrawal far from home Distance to home location large. Two Abstraction Rules keyed on Card with a 90 Day Search Interval and Function Type Median, over Latitude and over Longitude, give a crude home centroid, and a Require step on TxnType gates the test to ATM withdrawals. The median misplaces accounts with bimodal travel, the window should exclude the current withdrawal, and the 500 km distance is an illustrative placeholder. Matched = Payload.TxnType.RequireEqual("ATM").Against(Payload.Latitude).MatchDistanceKmAbove(Payload.Longitude, Abstraction.HomeLatitude, Abstraction.HomeLongitude, 500) Tag: Geo · Fraud · Card · single event
    8.1-06 Transaction far from last transaction Distance to previous location. The rolling form of 8.1-01: Abstraction Rules keyed on Card with Offset Type Last and Function Type Actual Value return the immediately prior coordinates, so there is no window beyond the lookback. The 50 km distance is an illustrative placeholder. Matched = Payload.Latitude.MatchDistanceKmAbove(Payload.Longitude, Abstraction.PrevLatitude, Abstraction.PrevLongitude, 50) Tag: Geo · Fraud · Card · rolling
    8.1-07 Transaction far from device location Mobile GPS versus transaction location. A single Activation Rule compares the device GPS pair with the transaction pair, with DeviceLatitude and DeviceLongitude as placeholder fields that the payload contract does not yet carry. The 1 km distance is an illustrative placeholder, and mobile GPS can itself be spoofed (see 8.3-14). Matched = Payload.DeviceLatitude.MatchDistanceKmAbove(Payload.DeviceLongitude, Payload.Latitude, Payload.Longitude, 1) Tag: Geo · Fraud · Account · single event
    8.1-08 Merchant distance from billing address Spend far from home with no prior travel. Distance of the merchant from the billing address. Upstream fields: Payload.MerchantLatitude, Payload.MerchantLongitude, Payload.BillingLatitude and Payload.BillingLongitude, supplied before Jube or by an inline-script hook. Distance 500 km is an illustrative placeholder. Matched = Payload.MerchantLatitude.MatchDistanceKmAbove(Payload.MerchantLongitude, Payload.BillingLatitude, Payload.BillingLongitude, 500) Tag: Geo · Fraud · Card · single event
    8.1-09 IP location far from billing/home address IP geolocation mismatch. Distance of the IP location from the account home centroid.     8.5-17 Many vendors geocoded to one location Vendor cluster. Matched = Abstraction.VendorsAtCell.MatchGreater(5) Check: Geohash-7 cell size (about 150 m) should be verified against the geohash cell table. Tag: Geo · Fraud · Location · lifetime
    8.5-18 Charity payments to conflict zones (NPO) Conflict-area proximity.     8.5-19 Vessel AIS gap near sanctioned ports (trade) Dark activity. Matched = Payload.NearestPortCode.RequireInList(List.SanctionedPorts).Against(Abstraction.AisHoursSincePrev).MatchGreater(24) Check: The gap length is an analyst parameter; verify the sanctioned port list against current designations.     8.5-20 Shipment route deviation through high-risk ports Route anomaly. A List holds the high-risk ports and a Require step gates on them. Matched = Payload.TransitPortCode.RequireInList(List.HighRiskPorts).Against(Payload.RouteTransitPortKey).MatchNotInList(List.DeclaredRouteTransitPairs) Check: Verify the high-risk port list against current policy and sanctions sources. Tag: Geo · AML · Shipment · voyage
